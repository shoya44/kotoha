## 会話（テキスト）

```
ブラウザ                     サーバー                        外部
   │
   │ POST /api/chat
   │ {"text": "ただいま"}
   ├──────────────────────────>│
   │                           │ ① トークン検証
   │                           │ ② ロック取得
   │                           │ ③ 発言を保存してコミット
   │                           │ ④ 直近の会話を読む
   │                           │ ⑤ Fast / Slow を決める
   │                           │ ⑥ 記憶を集める
   │                           │ ⑦ プロンプトを組む
   │                           │                    生成
   │                           ├───────────────────────────>│
   │                           │<───────────────────────────┤
   │                           │ ⑧ 内部タグを外す
   │                           │ ⑨ 返答・機嫌・利用実績を保存
   │ {"reply": "…", "mode":…}  │ ⑩ ロック解放
   │<──────────────────────────┤
   │ ⑪ 画面に出す
   │ ⑫ 読み上げ（設定が有効なら）
```

| 手順 | 内容 |
|---|---|
| ① | `X-Kotoha-Token` ヘッダーを照合。不一致なら401 |
| ② | プロセス内のロック。巡回処理と共有する |
| ③ | `turn_id` は既存の最大値＋1。ここでコミットするので、以降が失敗しても発言は残る |
| ④ | 最大 `RECENT_TURNS × 2` 件。合計が `RECENT_CHARS` を超えるあいだ古いほうから捨てるが、最後の1件は必ず残す。いま保存した発言が末尾にあれば、二重に載らないよう外す |
| ⑤ | [記憶の想起](#記憶の想起)を参照 |
| ⑥ | 同上。意味で探すぶんだけ、同じPC内のOllamaへ1往復する（約60ms）。応じなければタグ検索だけで進む |
| ⑦ | [プロンプトの組み立て](#プロンプトの組み立て)を参照 |
| ⑧ | `[USED:…]` と `[MOOD:…]` を本文から取り除く |
| ⑨ | 返答本文、`last_conversation_at`、機嫌、想起した記憶の利用実績、再固定化の候補 |
| ⑪ | 吹き出しを追加。`mode` はヘッダー右に出す |
| ⑫ | [発話](#発話)を参照 |

生成に失敗した場合、返答は保存されません。③で発言だけが残るので、送り直すと新しい `turn_id` になります。同じターンの重複を除く仕組みはありません。

### 保存する内容（⑨）

| 対象 | 値 |
|---|---|
| `messages` | 内部タグを外した返答本文 |
| `app_state.last_conversation_at` | 現在時刻（UTC） |
| `app_state.mood` / `mood_at` | `[MOOD:…]` が既知のラベルだったときだけ更新 |
| `memory_nodes.last_used_at` / `expires_at` | `[USED:…]` のIDについて。期限は層ごとの日数ぶん延長 |
| `memory_tags.use_count` / `last_used_at` | 同上。use_count は3で頭打ち |
| `app_state.pending_reconsolidation_ids` | `[USED:…]` のIDを先頭に足し、重複を除いて最大50件 |

## 会話（通話）

通話はブラウザ側だけの機能です。サーバーから見ると、テキストの会話と同じ `/api/chat` が呼ばれているだけです。

```
  電話ボタン
      │
      ├─ 間つなぎの音声をまとめて作る（待たない）
      │
      ▼
  ┌ 聞き取り ────────────────────────────────────┐
  │                                              │
  │  話し終わり（speechend）── 時刻を覚える        │
  │      │                                       │
  │      │ 認識が確定（result）                    │
  │      ▼                                       │
  │  POST /api/chat ──────┐                      │
  │      │                │ 0.4秒たっても         │
  │      │                │ 返答がなければ        │
  │      │                ▼                      │
  │      │            「えっと…」                 │
  │      │                │                      │
  │      │                ▼ 0.45秒あける          │
  │      ▼                │                      │
  │   返答 ───────────────┴──> 文ごとに読み上げ    │
  │                                    │         │
  └────────────────────────────────────┘         │
         読み上げが終わったら聞き取りに戻る          │
```

### 通話の持ち主

通話できるのは1台までです。サーバーが持ち主の名札（端末がランダムに作る文字列）と最後に確認した時刻を覚えています。

```
通話をはじめる  → POST /api/call  名札を置く。先客がいれば入れ替わる
通話のあいだ    → GET  /api/call  5秒ごとに「まだ自分の番か」を確かめる
                                  自分でなければ黙って通話をやめる
通話をやめる    → DELETE /api/call  名札を消す
```

確認が2分途切れた名札は無効として扱うので、PCが落ちたまま記録が残っても通話中のままにはなりません。取り上げられた側は名札を消しません。新しい持ち主の記録まで消してしまうためです。

### 聞き取り

ブラウザの Web Speech API を使います。`continuous = false` / `interimResults = false` / `lang = "ja-JP"` で、1回の発話ごとに確定結果を1つ受け取ります。

- 認識は発話が切れるたびに終わるので、`end` イベントで開き直します
- `no-speech` と `aborted` は通話の終わりではないので、黙って聞き直します
- `not-allowed`（マイク不許可）は通話を終了します
- **読み上げ中はマイクを開きません。** スピーカーのままでも自分の声を拾いません。そのぶん割り込みはできません

認識結果には句読点も疑問符も付きません。「もしもし聞こえる」のような形で届きます。

### 間つなぎ（フィラー）

| 項目 | 内容 |
|---|---|
| 語 | 「あっ…」「えっと…」「んー…」「うーん…」 |
| 音声 | 通話の開始時にまとめて合成し、通話中は使い回す |
| 鳴らす条件 | 通話中／話し終わりから0.4秒たっても返答が未着／音声が1つ以上ある |
| 起点 | 認識の確定時ではなく**話し終わりの検知時**。確定までの数百ミリ秒も待ち時間のうち |
| 鳴らしたあと | 0.45秒あけてから本文へ。すぐ続けると畳みかけるように聞こえる |
| 語の選択 | 直前と同じ語は避ける。1つしか用意できていなければ繰り返す |

待ち時間は固定です。発言の長さや言い回しでは変えていません。プロンプト1900字のうち発言が占めるのは14字ほどで、何を話してもことはが読む量はほぼ同じだからです。過去368往復で測った「発言の長さと返答の長さ」の相関は +0.24 と弱く、尋ねる言い回しを含む場合でも返答が1.2倍になる程度でした。

音声エンジンが応じないときは、間つなぎなしで動きます。

### 発話

読み上げは句点・感嘆符・改行で文に分け、**1つ目を鳴らしながら次を合成**します。

```
   0.0s  1つ目（15字）の合成をはじめる
   0.8s  合成おわり → すぐ2つ目の合成をはじめる
   0.8s  ▶ 1つ目を再生（音声は約3.3秒ある）
   1.6s  2つ目の合成おわり（再生中に余裕で間に合う）
   4.1s  ■ 1つ目おわり
   4.1s  ▶ 2つ目を再生（待ちなし）
```

- 10文字に満たない断片は前につなぎます。細切れに合成すると間延びするためです
- 合計300文字で打ち切ります。切れ目のない長文は、その位置で切り詰めて読みます
- 音声の長さは合成時間の4倍前後あるので（★15字で合成0.78秒・音声3.26秒）、1つ目を鳴らしているあいだに残りは作り終わります
- 世代番号で打ち切れるようにしてあり、通話を切ると次の文へ進みません
- 音声エンジンへの接続は開いたまま使い回します。1文ごとにつなぎ直していたときは0.44秒ぶん余計にかかっていました
- エンジンが再起動すると、開いたままの接続は黙って切れています。そのときだけ一度つなぎ直します

#### 鳴らす側（ブラウザ）

iPhoneは、**画面に触れた流れの中でしか音を鳴らさせません**。返答の声が届くのは通信を終えたあとで、そのときにはもう指の流れが切れています。そこで、

```
通話ボタン／送信／「声で話す」の切り替え を押した指の動きで
      ↓
音の出口（AudioContext）を開けて、無音をひとつ鳴らして許可を取る
      ↓
以後はそこへ流し込む。通信のあとでも鳴らせる
```

- 鳴らすたびに `Audio` を作る書き方だと、作ったものが毎回「触れていない」ものとして弾かれ、**PWAで無音**になります
- 受け取った wav は届いた時点で音に変えて持ちます。鳴らすときに待ちがありません
- iOS 16.4以降は `navigator.audioSession` を `playback` にして、**着信スイッチが消音でも鳴らします**
- 途中で止めたときも「鳴り終わった」として扱うので、次の文を待ち続けることはありません

## プロンプトの組み立て

空のブロックは飛ばし、残りを空行2つでつないで、1件のuserメッセージとして送ります。

| 順 | ブロック | 出どころ | 実測 |
|---:|---|---|---:|
| 1 | 固定ルール | `prompts/fixed_rules.txt` | 744字 |
| 2 | 人格 | `prompts/persona.txt` | 330字 |
| 3 | 時刻・自分・相手の様子 | 下記 | 162字 |
| 4 | 基本情報 | 保護記憶 最大5件 | 79字 |
| 5 | 関連記憶 | 想起した記憶 最大6件 | 370字 |
| － | PCの中身・できること | **機械の話のときだけ** | 0字／約250字 |
| 6 | 直近の会話 | 最大5往復・3,000字 | 199字 |
| 7 | 今回の発言 | 入力そのまま | 14字 |
| | 合計 | | **約1,840字** |

実測は会話が途切れている状態のものです。続けて話すと6が積み上がり、4,700字ほどまで増えます。

記憶の各行は `- [id:12][09-17][fact] 本文` の形です。日付はエピソードなら発生日、意味記憶なら確認日を使い、今年のものは年を省きます。

層（episode / semantic）は書きません。種類から決まるからです（`event` なら出来事、それ以外は意味記憶）。以前は `[id:12][2026-09-17][semantic/fact]` と36字あり、ラベルだけで本文と同じ量を占めていました。`id` は `[USED:]` で返してもらうので、そのまま残しています。

### PCの中身（機械の話のときだけ）

空き容量・メモリ・CPU・GPUは**毎回渡しません**。250字ほどあるうえ、ほとんどの会話では要らないためです。
発言に機械まわりの語（容量・メモリ・CPU・重い・エンジン・Ollama…）が含まれたときだけ足します。
語の一覧は `talk/presence.py` の `MACHINE_WORDS` です。

```
PCの中身: Cドライブ 空き98GB（89%使用）、メモリ47%使用（空き16.8GB）、CPU15%、GPU11%・VRAM2.3/8GB・60℃
頼まれたらできること: 音声エンジンを起こす / 音声エンジンを止める / Ollamaを起こす / Ollamaを止める / 自分を入れ直す
（やるときは返答の最後に [DO: 名前] を付ける。名前は上のとおりに書く。頼まれていないのに付けない）
```

**できることの一覧も同じ枠に入れています。** 機械の話でないときは渡らないので、関係のない場面で操作を思いつくことがありません。

> ⚠️ **CPUは前回の巡回からの平均**です。瞬間値を測ると0.1秒待たされるので、巡回のたびに基準を取り直しています。

### ことはから何か言う（`announce`）

自発的な発言は**すべてここを通します**。通知だけ送る道はありません。

置き場は `serve/announce.py` です。**ファイルが分かれていること自体が約束**で、`notify.push()` を呼ぶのはこの中だけです。巡回（`serve/jobs.py`）は `announce()` を呼ぶだけで、通知の中身を組み立てません。

```
announce(conn, 今回言うこと, 代わりの一言)
  ├ chat.speak()   人格・記憶・時刻・相手の様子は普段どおり。「今回の発言」だけ差し替え
  ├ 履歴に残す     ← 開けば会話に並んでいる
  └ notify.push()  ← 残ったことの結果として通知
```

**言えなかったら鳴らしません。** 開いても何も無い通知は不親切ですし、あとから会話を辿れなくなります。

ただし見張りのように「黙るくらいなら定型でも伝えたい」ものには、代わりの一言を渡せます。その場合も**定型文を履歴に残してから**送ります。

#### 立て続けに鳴らさない

同じ巡回で朝のひとことと頼まれごとが重なることがあります。2通に分けると、同じ人から立て続けに届きます。そこで**巡回のあいだは鳴らさずに預かり**、最後に1通へまとめます。

```
巡回 ┬ maybe_reminders  ─┐
     ├ maybe_briefing   ─┤ 預かる（app_state.held_announcements）
     ├ maybe_lookout    ─┤
     ├ maybe_reach_out  ─┘
     └ flush_held()      → まとめて chat.speak() 1回 → 通知1通
```

前の通知からの間隔は `KOTOHA_NOTIFY_GAP_MINUTES`（既定10分）で、これより近いものは次の巡回へ持ち越します。**預かりはDBに置く**ので、落ちても頼まれごとは消えません。0にすると、まとめずにその場で鳴らします。

まとめるときは、理由を並べて「ひと続きの短い言葉にまとめて言う」と頼みます。**どう言うかはことはに任せます。** 箇条書きの通知にはしません。

預かれるのは8件までです。それを超えると古いほうから捨て、捨てたことを `data/notify.log` に残します。

**言えなかったときは、預かりを消しません。** 頼まれごとは預かった時点で「言った」ことにしてあるので、ここで落とすと二度と出てきません。ただし言えるまで毎分試すとそのたびにAPIの枠を食うので、3回続いたら諦めて `data/notify.log` に残します（記憶整理と同じ考え方）。

> ⚠️ **預かったときも、呼び出し側から見れば「言えた」です。** そうしないと、頼まれごとが毎分積み増されます。

> ⚠️ **自発的な発言では操作をさせません。** `[DO:]` が付いていても捨てます。

#### あとでもう一度（スヌーズ）

頼まれごとの通知だけ、開く先に番号を足します。

```
通知 ─ url: …/?remind=12       ← 開いた画面にボタンを出す（iPhoneはこちら）
     └ web_buttons[0].url:
            …/?snooze=12       ← 通知のボタンから直に（Chromeだけ）
                │
                ▼
        POST /api/remind/snooze {ids:[12]}
                │
                └ remind.snooze() … 同じ用件で新しい1件を入れる
```

**Safariは通知のボタンに対応していません**（Chromeは最大2個まで）。iPhoneのPWAでは出ないので、開いた画面に一度だけ押せるボタンを出します。押した跡は `history.replaceState` でURLから消し、読み込み直しても効かないようにします。

URLに載せるのは**番号だけ**です。通知はOneSignalを通るので、用件そのものは渡しません。まとめて言ったぶんは番号を並べるので、まとめて置き直せます。

### 頼まれごとを預かる（`[REMIND:]`）

`[DO:]` と同じ仕組みです。返答の末尾に付いたタグを外して `reminders` に入れ、巡回で時刻が来たら `announce()` に渡します。

```
[REMIND: 2026-09-18 09:00|歯医者]
```

時刻の読み替えは向こうに任せます。現在時刻はプロンプトに入っているので、「10分後」を絶対時刻で書かせるほうが、こちらで日本語を解釈するより確実です。**読めない時刻は黙って捨てます。** 妙な予定を抱え込むより、そのほうがまし。

> ⚠️ **速い道でも預かります。** ここで捨てると、本人は「覚えとくね」と言ったのに何も残りません。実際、最初はそう作ってしまっていました。

> ⚠️ **自発的な発言では預かりません。** 自分で自分に予定を作らせないためです。

預かっているものはプロンプトにも載せます。聞かれたら答えられます。

PCを閉じていた間に過ぎたものは、12時間より古ければ黙って畳みます。言えなかったものは畳まないので、次の巡回でもう一度試します。

### 見守り

| 気づくこと | 条件 | 間隔 |
|---|---|---|
| 根を詰めすぎ | 同じアプリを3時間 | 声をかけたら数え直す |
| 夜更かし | 2時〜5時に操作している | 一晩に一度 |

前面アプリの計測は `presence.sample()` が毎分やっていたものです。そこに「同じアプリが続いている間、始まった時刻を覚える」を足しただけで、新しく覗くものはありません。

### 朝のひとこと

巡回の中で、その日まだ言っていなくて、8時を過ぎていたら一度だけ。`last_briefing_on` に日付を持ちます。

8時にPCが寝ていた場合は、起きたときに言います。ただし**3時間まで**。夕方に「おはよう」と言われても困るので、遅れすぎた日は黙って、その日の分として畳みます。

**印は文を作る前に付けます。** 作るのに失敗しても、毎分やり直してAPIを空回りさせないためです。

空模様は Open-Meteo から。傘と服装はPython側で決め、事実だけ渡して言い方はことはに任せます。

```
今日の空模様:
  くもり / 最高21℃ 最低14℃ / 降水確率20%
  傘: いらない
  服装: 長袖
```

天気が取れなければ、この塊が空になるだけです。挨拶自体は出ます。

### 暇なときの声かけ

60秒の巡回で、3つとも満たしたときだけ。APIを1回使うので頻繁には出しません。

| 条件 | 既定 |
|---|---|
| 会話が途切れてから | 5時間 |
| 前回の声かけから | 6時間 |
| 時間帯 | 9時〜23時 |

文は普段と同じ組み立てで作ります。人格も記憶も時刻も相手の様子も渡し、最後の「今回の発言」だけを差し替えます。

```
いまは話しかけられていない。しばらく間が空いたので、そちらから一声かける。
一行だけ、短く。用がなくてもいい。記憶にある小さなことに触れてもいい。
返事を求めすぎない。責めない。
```

出てきた文は**会話として履歴に残し**、そのうえで通知を送ります。開けば会話に並んでいます。

> ⚠️ **声かけでは操作をさせません。** `[DO:]` が付いていても捨てます。頼まれてもいないのに動かすのは、管理人の仕事ではありません。

> ⚠️ **声をかけると決めた時点で記録します。** 文を作る前に印を付けるので、生成に失敗しても続けて何度も試しません。

### 見張り（落ちたとき・空きが減ったとき）

巡回の外側で回します。止まっている相手を確かめるのに1秒ずつかかるので、会話の順番待ちに並べると毎分そのぶん止まります。

**状態が変わった瞬間だけ**知らせます。ずっと止まっているものについて毎分言われても困るためです。起動直後から止まっていた場合も、最初の1回は知らせません。

### 頼まれごと（`[DO:]`）

`[USED:]` `[MOOD:]` と同じ仕組みです。返答から剥がし、**表にある名前のときだけ**動かします。

```
ことは: 「ん、しょうがないなあ」[DO: Ollamaを起こす]
          ↑ 画面にはここまで      ↑ 剥がして実行
```

| | |
|---|---|
| できること | `talk/actions.py` の `ACTIONS` にあるものだけ |
| 動かす順 | **返答を保存し終えてから**。入れ直しならそこで落ちる |
| 記録 | 何をしたか・しなかったかを `data/actions.log` へ |
| 止め方 | `.env` の `KOTOHA_ACTIONS_ENABLED=false` |

> ⚠️ **止める操作は、実行ファイルのフルパスで狙います。** `run.exe` のようなありふれた名前を名前だけで狙うと、無関係なものまで巻き込みます。

> ⚠️ **表に無い名前は黙って捨てます。** ことはが好きなコマンドを組み立てられる作りにはしていません。

### 時刻ブロック（3）

```
現在: 2026-09-17 13:26（木曜日）
前回の会話: 3日前
今のことは: 夜更かし中で、ゲームかスマホを触っている
今の機嫌: ふつう（とくに変わったところはない）
覚えていること: 76件（最後に整理したのは2時間前）
相手の様子: PCは6時間つけっぱなし、この1時間はVS Codeを触っている（32分ほど）
```

下2行はFastでは付けません（保護記憶だけを積む道なので、自分語りの材料も渡しません）。

| 行 | 決め方 |
|---|---|
| 現在 | ローカル時刻。曜日は日本語 |
| 前回の会話 | `last_conversation_at`（UTC）からの経過を「たった今／3分前／5時間前／昨日／3日前／1週間前／2か月前／1年以上前」に言い換える。UTCのまま渡すと時差ぶん開いて見えるため |
| 今のことは | 時間帯ごとの様子。区切りは画面のアバター切り替え（`getAvatarGroup()`）と揃えてある |
| 今の機嫌 | `app_state.mood`。6時間を過ぎたものは「ふつう」に戻す |
| 覚えていること | 期限切れでない記憶の件数と、最後に整理した時刻からの経過 |
| 相手の様子 | PCを起動してからの時間と、この1時間でいちばん触っていたアプリ |

> ⚠️ **「相手の様子」というラベルを変えないでください。** 「PCの様子」と書くと機械の計測値に見えて返答に使われません。同じ内容でも、ラベルを変えるだけで挙動が変わります。

## 自分のことを知っている

ことはは、自分が何者で、何ができるようになったかを持っています。出どころは2つです。

| | 中身 | どこから |
|---|---|---|
| **今の状態** | 覚えている件数、最後に整理した時刻 | 時刻ブロックに毎回入る |
| **できるようになったこと** | 更新の履歴 | **記憶として持つ**（ピン留め） |

更新はプロンプトの欄ではなく、**記憶**として書き込みます。

```
kotoha.bat note "ことはは9月17日から、意味の近い記憶を思い出せるようになった。"
```

`semantic/fact`・**期限なし**・**ピン留め**で入ります。ピン留めにするのは、自分が何者かは想起で引き当てるものではなく、常に持っているものだからです。基本情報の枠は5件までなので、**新しい5件が出ます**。古いものは残り、タグ（`ことは` / `更新`）や意味の近さで引けます。

> ⚠️ **基本情報の枠を更新の履歴で埋め切らないでください。** ほかにピン留めしたい事実があるなら、画面から外せます。

## Geminiとのやりとり

### 送るもの

OpenAI互換の `/chat/completions` に、httpx で1回のPOSTを送ります。ストリーミングは使いません。

```json
{
  "model": "<GEMINI_MODEL>",
  "messages": [{"role": "user", "content": "<組み立てたプロンプト>"}],
  "max_tokens": 1024,
  "temperature": 0.8
}
```

`model` / `max_tokens` / `temperature` は設定値です（既定は順に `gemini-3.5-flash-lite` / 1,024 / 0.8）。整理のときだけ `max_tokens` を 1,500 に上げます。

system ロールは使わず、固定ルールも人格もすべて1件のuserメッセージに含めます。会話も記憶も履歴として渡すのではなく、テキストとして埋め込みます。

### 受け取るもの

`choices[0].message.content` を取り出します。本文の末尾に内部制御タグが付きます。

内部タグは4つあり、**扱いはすべて同じ**です。当てはまるときだけ付き、無ければ何も付きません。

| タグ | 用途 | 扱い |
|---|---|---|
| `[USED: 1,2]` | 使った記憶のID | 数字だけ取り出す。Fastでは保護記憶のIDだけ通す |
| `[MOOD: 眠い]` | 機嫌が変わったとき | 5つのラベル以外は捨てて直前の機嫌を保つ |
| `[REMIND: 時刻\|用件]` | 頼まれごと | 形が揃っているものだけ預かる |
| `[DO: 名前]` | 頼まれた操作 | 表にある名前のときだけ動かす |

以前は `[USED:]` だけ「使わなければ空で付ける」という別の作法でした。空のタグという形を覚えたモデルが、それを他のタグへ持ち込み、**`[REMIND: ]` が画面に出ました**。作法を1つに揃えてあります。

値を取り出したあと、`chat.strip_tags()` で**もう一度ひと拭き**します。閉じ括弧が欠けても全角の `［］：` でも中身が空でも落とすので、形が崩れたタグが画面に出ることはありません。取り出す側は形の揃ったものだけを拾う（妙な予定を抱え込まない）ので、**厳しい側と緩い側を分けてあります。**

### 失敗したとき

| 状況 | 動作 |
|---|---|
| 通信エラー / 5xx / 空の応答 | 同じ内容で再試行。合計 `LLM_ATTEMPTS`（既定2）回まで。待ち時間は入れない |
| 429（レート超過） | **再試行せずエラー**。分あたりの枠は間を置かずに投げ直しても空いておらず、失敗したぶんも枠を食うため |
| 400 / 401 | 即エラー。キーやモデル名の問題として扱う |
| その他の非200 | 即エラー |
| 応答の形が違う | 即エラー |

失敗しても作り話は保存しません。CUIは画面に出し、WebはHTTP 502を返します。

## 記憶の想起

### Fast / Slow

`KOTOHA_FAST_ENABLED` は既定で `false` なので、**通常はすべてSlowを通ります**。有効にした場合の判定は次のとおりです。

```
FAST_ENABLED が false            → slow
入力が FAST_MAX_CHARS（40字）超  → slow
質問・過去参照・記憶操作の語を含む → slow
入力が登録済みタグと一致          → slow
それ以外                         → fast
```

Fastは保護記憶だけを積みます。意味での探索も行いません。返答の1行目が `NEEDS_SEARCH` なら、同じターンのうちにSlowで生成し直します（`mode` は `slow+fallback`）。別のモデルに切り替えるわけではありません。

### 集め方（Slow）

```
① 入力＋直近の会話に、登録済みタグが文字として含まれるか調べる
      │
      ├─ 含まれる ──> ② そのタグを持つ記憶を集める            最大40件
      │                    並び順: タグの利用回数
      │                          → 記憶の最終利用日時
      │                          → 確認日時
      │                    │
      │                    └─> ③ ②の記憶から1本たどった先を足す  最大40件
      │                         （意味の近い記憶を結んだ接続をたどる）
      │
      └─ 含まれない ─────────────────┐
                                     │
④ 最近のエピソードと継続話題を足す ←──┘（タグの一致に関わらず必ず行う） 最大10件
      ↓
⑤ 意味の近い記憶を別に探す（①〜④で出なかったものだけ）      予約2件
      ↓
⑥ IDで重複を除き、保護記憶を別枠にして、残りを6件まで
```

②と③はタグが一致したときだけ動きます。④は毎回動くので、タグが1つも当たらなくても最近の出来事と続いている話題は渡ります。

- タグ照合は**部分一致**です。タグの文字が発言にそのまま含まれていなければ当たりません
- ⑤は文字ではなく**意味の近さ**で探します。「眠れない」から睡眠薬の記憶にたどり着けるのはこちら
- ③がたどる接続は、座標づけの巡回が自動で張ります。効くのは②が1〜3件のときで、実発言では**18%**。②が0件だと③は動かず、4件以上だと枠が先に埋まります
- 期限切れの記憶はすべての段階で除きます
- ②の並び順により、よく思い出す記憶が先に来ます。利用回数は0〜3で頭打ち、30日使わなければ0に戻るので、古い記憶が居座り続けることはありません
- 保護記憶は別に最大5件取ります（④とは独立）

#### ⑤ 意味で探す

タグは記憶整理が付ける名詞（病院、タバコ、出前館）ですが、人は気分と動詞で話します。実際の発言406件では、タグが当たったのは151件でした。残りは話題に関係なく「最近あったこと」を返していたことになります。

照合には**直前のやりとり2行＋今回の発言**を使います。発言の長さは中央値14字しかなく、「しんどい」だけでは意味が定まらないためです。

6枠のうち**2枠を予約**します。後ろに足すだけだと、タグが当たった回は枠が埋まりきって出番が来ません。近さが `KOTOHA_EMBED_FLOOR` に届かなければ何も出さないので、**近い記憶が無い回は今までどおり**です。

```
6枠 ┌─ タグ命中・直近の出来事   4枠
    └─ 意味で選んだ記憶         2枠（無ければ上が広がる）
```

Ollamaが止まっていても会話は続きます。読み上げと同じ扱いで、想起がタグ検索だけに戻ります。一度失敗したら `KOTOHA_EMBED_RETRY_SECONDS` のあいだは試さないので、止まっている間に会話が待たされることもありません。

## 記憶整理

### いつ走るか

| きっかけ | 条件 |
|---|---|
| CUI 起動時・返答後 | 未処理が `CONSOLIDATE_TURNS`（10）ターン以上 |
| CUI `/consolidate` | 無条件 |
| Web 巡回（60秒ごと） | 未処理があり、**最後の会話から5分以上たっている** |
| `kotoha.bat consolidate` | 無条件 |

Web が会話中に走らせないのは、巡回が `/api/chat` と同じロックを取るためです。整理のあいだ返答が数秒止まり、通話ではそれが沈黙になります。1回で20ターンまで処理できるので、溜めても間があけば追いつきます。

### ベクトルを作る（記憶整理とは別）

想起で使う「意味の座標」は、記憶整理ではなく**60秒の巡回が別に作ります**。

| | |
|---|---|
| きっかけ | 巡回のたび。ベクトルの無い記憶があれば作る |
| 1回の件数 | 最大 `KOTOHA_EMBED_BATCH`（32件） |
| ロック | **取らない。** 会話の順番待ちには並ばせない |
| ついでにやること | 座標がついた記憶を、意味の近い記憶と**結ぶ**（想起③がたどる先） |
| Ollamaが止まっているとき | 何も作らず、次の巡回でやり直す |

記憶整理から切り離してあるので、Ollamaが止まっていても記憶は今までどおり作られます。ロックを取らないのは、変換がOllamaへの往復で時間がかかるためです。ここで順番待ちに入ると、そのあいだ会話が止まります。

記憶が71件あるとき、初回は3巡（約3分）で埋まります。1件4,096バイト、71件で284KBです。

### 流れ

```
① 未処理の発言を切り出す
      last_processed_message_id より後で extractable=1
      最大20ターン・20,000字
      先頭の1件は上限を超えていても必ず含める
      ↓
② 再固定化の候補を読む
      pending_reconsolidation_ids のノード
      ↓
   ①も②も空 → 何もせず終了（APIを呼ばない）
      ↓
③ プロンプトを組む
      consolidation_system.txt
      ＋ 未処理の会話（[id:N] 付き）
      ＋ 既存の記憶（会話に含まれるタグから最大10件）
      ＋ 最近使われた記憶（②）
      ↓
④ Gemini に投げる（max_tokens 1,500）
      ↓
⑤ 最初の { から最後の } までをJSONとして読む
      読めなければエラー。処理位置は進めない
      ↓
⑥ 中身を検証して保存
      既存と言い方が違うだけの候補は作らず、既存を確かめ直す
      ↓
⑦ 後始末
      last_processed_message_id を①の末尾へ
      last_consolidation_at を更新
      pending_reconsolidation_ids を空に
```

①で先頭の1件を必ず含めるのは、上限を超える発言が1つ来たときに空を返すと、処理位置が永久に進まなくなるためです。長すぎる本文はプロンプト生成時に切り詰めます。

### JSONの検証（⑥）

モデルの出力はそのままでは信用せず、項目ごとに落とします。

**new_nodes**（最大8件）

| 条件 | 満たさないとき |
|---|---|
| `layer` が episode または semantic | その要素を捨てる |
| semantic の `kind` が fact / preference / open_topic / procedure | 捨てる（episode は event に固定） |
| `text` が空でなく、episode 400字・semantic 200字以内 | 捨てる |
| `source_message_ids` に今回のバッチ内のIDが1つ以上ある | 捨てる |

通ったものは `source_key = batch:<先頭id>-<末尾id>:<番号>` で登録します。同じキーがあれば無視されます。期限は最初の根拠発言の日時にエピソード30日／意味記憶180日を足した値です。タグは前後の空白を詰めて24字まで、最大3個です。

**edges**：`relation` が `derived_from` で、from/to がどちらも今回作れたノードを指しているものだけ登録します。

**reconfirm_ids**：整数のIDについて確認日時を更新し、期限を延長します。

**重複の寄せ**：`new_nodes` の各候補を座標に直し、既存の記憶と `KOTOHA_EMBED_MERGE_FLOOR` 以上に近ければ**作らずに既存を再確認**します。出典だけは既存へ付け替えるので、どの会話で確かめたかは残ります。

同じ出来事が何件にも分かれると、想起の6枠が同じ話で埋まります。実測では記憶76件のうち29件が何かと重なっていました。ただし近いだけで別の事実ということもあるため（「Rocket Now」と「出前館」は0.85で近いが別の店）、しきい値は**言い直しだけを拾う高さ**に置いてあります。

**updates**（最大4件）：本文を200字までに切り、確認日時の更新・期限の延長・出典の追加・タグ利用回数のリセットを行います。根拠IDが今回のバッチ内にないものは捨てます。本文が変わるとベクトルは古くなるので、ここで捨てます（次の巡回で作り直されます）。

会話中に記憶の本文が書き換わることはありません。既存ノードの自動統合と、承認を挟む仕組みはありません。

## 所要時間の目安

通話で話しかけてから声が返るまでの内訳です。★は実測、それ以外は目安です。

| 段階 | 時間 | 変わる要因 |
|---|---|---|
| 認識の確定 | 0.3〜0.8秒 | 発話の長さ、ネットワーク |
| ロック待ち | 通常 0秒 | 忘却やバックアップと重なったとき |
| 記憶検索・組み立て | 約0.06秒 | ★意味で探すぶんの往復。タグだけなら1ミリ秒 |
| 最初の1文字まで | 0.3〜1.0秒 | プロンプト長（1,840〜4,600字） |
| 生成 | 0.3〜0.8秒 | 返答の長さ（★平均25字） |
| 音声合成（1文目） | 0.6〜1.1秒 | ★0.25秒＋文字数×0.035秒 |
| | **合計 1.6〜3.8秒** | |

音声合成は、接続を使い回すようにして**1文あたり0.44秒縮みました**（固定ぶんが0.74秒から0.25秒へ）。かつては群を抜いて重い段階でしたが、いまは生成待ちと同じくらいです。文ごとに分けて先読みする仕組みは引き続き効いています。

テキストの会話では認識と合成がないぶん、返答が出るまで1〜2秒ほどになります。

| 前回からの間隔の言い回し | `talk/chat.py` の `elapsed_phrase()` | サーバー再起動 |

プロンプトの3ファイルは毎回読み直しているので、**保存するだけで次の発言から効きます**。文面を試しながら詰めるときに便利です。

> ⚠️ **`MOODS` を変えたら `fixed_rules.txt` のラベル一覧も直してください。** 片方だけ変えると、モデルが返すラベルが未知の値になり、機嫌が一切変わらなくなります。ずれるとテストが落ちるようにしてあります。

> ⚠️ **`situation()` の時間帯を変えたら `serve/static/app.js` の `getAvatarGroup()` も直してください。** 画面のアバターと言うことが食い違います。こちらもテストで見ています。

### 会話の組み立て

| 変えたいこと | 直す場所 | 反映 |
|---|---|---|
| 参照する直近会話の量 | `.env` の `KOTOHA_RECENT_TURNS` / `_RECENT_CHARS` | サーバー再起動 |
| 返答の最大の長さ | `.env` の `KOTOHA_MAX_OUTPUT_TOKENS` | サーバー再起動 |
| 返答のばらつき | `.env` の `KOTOHA_TEMPERATURE` | サーバー再起動 |
| モデル | `.env` の `GEMINI_MODEL` | サーバー再起動 |
| 応答待ちの上限、再試行の回数 | `.env` の `KOTOHA_TIMEOUT_SECONDS` / `_LLM_ATTEMPTS` | サーバー再起動 |
| Fastルートの有効化と判定文字数 | `.env` の `KOTOHA_FAST_ENABLED` / `_FAST_MAX_CHARS` | サーバー再起動 |
| Fast/Slow を分ける語 | `talk/router.py` の `QUESTION_WORDS` ほか | サーバー再起動 |

> ⚠️ **`KOTOHA_RECENT_CHARS` を増やすと返答が遅くなります。** プロンプトがそのまま伸び、最初の1文字までの時間が延びます。既定の3,000字で、続けて話したときの全体が4,700字ほどです。

> ⚠️ **`KOTOHA_FAST_ENABLED=true` にすると、1ターンで2回生成することがあります。** Fastで足りないとモデルが判断すると `NEEDS_SEARCH` を返し、Slowでやり直すためです。

### 記憶

| 変えたいこと | 直す場所 | 反映 |
|---|---|---|
| 整理を始めるターン数（CUIのみ） | `.env` の `KOTOHA_CONSOLIDATE_TURNS` | 次回起動 |
| 会話が途切れたと見なす時間 | `.env` の `KOTOHA_IDLE_SECONDS` | サーバー再起動 |
| 巡回の間隔 | `.env` の `KOTOHA_BACKGROUND_INTERVAL_SECONDS` | サーバー再起動 |
| 1回の整理で扱う量 | `.env` の `KOTOHA_BATCH_TURNS` / `_BATCH_CHARS` | サーバー再起動 |
| 記憶の保持日数 | `.env` の `KOTOHA_EPISODE_DAYS` / `_SEMANTIC_DAYS` | サーバー再起動 |
| 想起する件数 | `.env` の `KOTOHA_PINNED_LIMIT` / `_RELATED_LIMIT` ほか | サーバー再起動 |
| 忘却を回す間隔 | `.env` の `KOTOHA_MAINTENANCE_SECONDS` | サーバー再起動 |
| 1回に作る記憶の上限（既定8件） | `memory/consolidate.py` の `MAX_NEW_NODES` | サーバー再起動 |
| 記憶本文の字数上限 | `memory/consolidate.py` の `_validate_and_save` | サーバー再起動 |

> ⚠️ **`KOTOHA_CONSOLIDATE_TURNS` はCUIだけで使います。** Webは会話が途切れてから整理する方式なので、この値を変えても挙動は変わりません。Web側の頃合いは `KOTOHA_IDLE_SECONDS` です。

> ⚠️ **保持日数を変えても、すでにある記憶の期限は書き換わりません。** 新しく作る記憶と、想起・再確認で延長するときに使われます。

> ⚠️ **記憶本文の字数上限を変えるときは、`consolidation_system.txt` に書いてある字数も揃えてください。** プロンプト側が400字と言っているのに検証が200字で切ると、作られた記憶が黙って捨てられます。

### 記憶の想起（ベクトル）

記憶を「意味の座標」に直して貯め、想起の6枠のうち2枠をそこから選ぶ仕組みです。

| 変えたいこと | 直す場所 | 反映 |
|---|---|---|
| 仕組み全体の有効・無効 | `.env` の `KOTOHA_EMBED_ENABLED` | サーバー再起動 |
| 意味で選ぶ枠数（0で従来どおり） | `.env` の `KOTOHA_EMBED_RESERVE` | サーバー再起動 |
| 出す近さの下限 | `.env` の `KOTOHA_EMBED_FLOOR` | サーバー再起動 |
| 照合に足す直前の行数 | `.env` の `KOTOHA_EMBED_CONTEXT_LINES` | サーバー再起動 |
| 失敗後に試さない時間 | `.env` の `KOTOHA_EMBED_RETRY_SECONDS` | サーバー再起動 |
| 重複とみなす近さ | `.env` の `KOTOHA_EMBED_MERGE_FLOOR` | サーバー再起動 |
| 記憶どうしを結ぶ近さ・本数 | `.env` の `KOTOHA_EMBED_LINK_FLOOR` / `_LINK_LIMIT` | サーバー再起動 |
| 使うモデル | `.env` の `KOTOHA_EMBED_MODEL` | サーバー再起動 |
| Ollamaの場所 | `.env` の `KOTOHA_EMBED_BASE_URL` | サーバー再起動 |
| Ollamaの自動起動 | `.env` の `KOTOHA_OLLAMA_AUTO_START` / `_OLLAMA_DIR` | 次回起動 |
| モデルを常駐させる時間 | `.env` の `KOTOHA_EMBED_KEEP_ALIVE` | サーバー再起動 |
| 会話のたびに待つ上限 | `.env` の `KOTOHA_EMBED_TIMEOUT_SECONDS` | サーバー再起動 |
| 裏で変換するときの上限 | `.env` の `KOTOHA_EMBED_BUILD_TIMEOUT_SECONDS` | サーバー再起動 |
| 1回の巡回で変換する件数 | `.env` の `KOTOHA_EMBED_BATCH` | サーバー再起動 |

> ⚠️ **`KOTOHA_EMBED_MODEL` を変えると、全部の記憶が作り直されます。** 71件で35秒ほど。古いモデルのぶんは残りますが、想起には使われません。

> ⚠️ **`KOTOHA_EMBED_KEEP_ALIVE` を短くしすぎないでください。** その時間だけ何も話さないとモデルが眠り、次の1回に1.7秒かかります（常駐中は56ms）。

> ⚠️ **Ollamaが止まっていても会話は続きます。** 想起がタグ検索だけに戻り、ベクトルは次の巡回で作り直します。読み上げと同じ扱いです。

> ⚠️ **`KOTOHA_EMBED_FLOOR` の 0.62 は暫定値です。** 実発言102件の中央値0.616から置いた数字で、この値では約半分の発言で発火します。しばらく使ってから実ログで決め直してください。下げるほど出番は増えますが、関係の薄い記憶で予約枠を潰します。

> ⚠️ **`KOTOHA_EMBED_RESERVE=0` にすると、この仕組みを入れる前と1件も変わらない想起に戻ります。** 切り戻しはこれで足ります。

> ⚠️ **`KOTOHA_EMBED_MERGE_FLOOR` を下げすぎないでください。** 記憶を寄せると、違っていたほうの情報は戻りません。0.85まで下げると「Rocket Nowにはまっている」と「出前館も使う」が同じものとして扱われます。**枠を1つ無駄にするより、取り違えるほうが損**です。

> ⚠️ **`KOTOHA_EMBED_LINK_LIMIT=0` で連結づくりを止められます。** 既に張った接続は残るので、たどるのをやめたいときは `memory_edges` を空にしてください。

### 外出先から直せるもの

画面の設定シートから直せるものは、ファイルを開かなくても変えられます。

| 変えたいこと | 画面の場所 | 直接直す場合 |
|---|---|---|
| 人格・決まりごと・整理の指示 | ことばを直す | `prompts/*.txt` |
| 返答のふり幅、返答の長さ、覚えている量、整理までの間、声の種類 | 設定を変える | `.env` |

> ⚠️ **「設定を変える」は `.env` を書き換えます。** コメント行と関係のない行は残しますが、書式が壊れていると読めなくなります。`settings.bat` で開いたときと同じファイルです。

### 共通の注意

- **編集するのは `.env` です。** `.env.example` は既定値の一覧なので、こちらを直しても `.env` にすでにある項目は上書きされません。`settings.bat` は `.env` に足りない項目だけを追記します。
- **`.env` を変えたらサーバーを止めて `start.bat` で入れ直してください。** 設定は起動時に一度だけ読みます。
- **数値には有効範囲があります。** 範囲外だと起動時に理由を表示して止まります。`settings.bat` の保存後チェックでも同じ検査が走ります。
- **`KOTOHA_DB_PATH` を変えてもデータは移りません。** 新しい場所に空のDBができます。移したいときはファイルを自分で移動してください。
- **`KOTOHA_BACKUP_KEEP` を減らすと、次のバックアップで古い世代が消えます。** 残したいファイルは先に別の場所へ退避してください。
- **変更したら `tests` を流してください。** 揃えるべき対のずれなど、いくつかは自動で気づけるようにしてあります。

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests
```
