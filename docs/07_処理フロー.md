## 会話（テキスト）

```
ブラウザ                     サーバー                        外部
   │
   │ POST /api/chat
   │ {"text": "ただいま"}
   ├──────────────────────────>│
   │                           │ ① トークン検証
   │                           │ ② ロック取得
   │                           │ ③ 発言を保存してコミット
   │                           │ ④ 直近の会話を読む
   │                           │ ⑤ Fast / Slow を決める
   │                           │ ⑥ 記憶を集める
   │                           │ ⑦ プロンプトを組む
   │                           │                    生成
   │                           ├───────────────────────────>│
   │                           │<───────────────────────────┤
   │                           │ ⑧ 内部タグを外す
   │                           │ ⑨ 返答・機嫌・利用実績を保存
   │ {"reply": "…", "mode":…}  │ ⑩ ロック解放
   │<──────────────────────────┤
   │ ⑪ 画面に出す
   │ ⑫ 読み上げ（設定が有効なら）
```

| 手順 | 内容 |
|---|---|
| ① | `X-Kotoha-Token` ヘッダーを照合。不一致なら401 |
| ② | プロセス内のロック。巡回処理と共有する |
| ③ | `turn_id` は既存の最大値＋1。ここでコミットするので、以降が失敗しても発言は残る |
| ④ | 最大 `RECENT_TURNS × 2` 件。合計が `RECENT_CHARS` を超えるあいだ古いほうから捨てるが、最後の1件は必ず残す。いま保存した発言が末尾にあれば、二重に載らないよう外す |
| ⑤ | [記憶の想起](#記憶の想起)を参照 |
| ⑥ | 同上 |
| ⑦ | [プロンプトの組み立て](#プロンプトの組み立て)を参照 |
| ⑧ | `[USED:…]` と `[MOOD:…]` を本文から取り除く |
| ⑨ | 返答本文、`last_conversation_at`、機嫌、想起した記憶の利用実績、再固定化の候補 |
| ⑪ | 吹き出しを追加。`mode` はヘッダー右に出す |
| ⑫ | [発話](#発話)を参照 |

生成に失敗した場合、返答は保存されません。③で発言だけが残るので、送り直すと新しい `turn_id` になります。同じターンの重複を除く仕組みはありません。

### 保存する内容（⑨）

| 対象 | 値 |
|---|---|
| `messages` | 内部タグを外した返答本文 |
| `app_state.last_conversation_at` | 現在時刻（UTC） |
| `app_state.mood` / `mood_at` | `[MOOD:…]` が既知のラベルだったときだけ更新 |
| `memory_nodes.last_used_at` / `expires_at` | `[USED:…]` のIDについて。期限は層ごとの日数ぶん延長 |
| `memory_tags.use_count` / `last_used_at` | 同上。use_count は3で頭打ち |
| `app_state.pending_reconsolidation_ids` | `[USED:…]` のIDを先頭に足し、重複を除いて最大50件 |

## 会話（通話）

通話はブラウザ側だけの機能です。サーバーから見ると、テキストの会話と同じ `/api/chat` が呼ばれているだけです。

```
  電話ボタン
      │
      ├─ 間つなぎの音声をまとめて作る（待たない）
      │
      ▼
  ┌ 聞き取り ────────────────────────────────────┐
  │                                              │
  │  話し終わり（speechend）── 時刻を覚える        │
  │      │                                       │
  │      │ 認識が確定（result）                    │
  │      ▼                                       │
  │  POST /api/chat ──────┐                      │
  │      │                │ 0.4秒たっても         │
  │      │                │ 返答がなければ        │
  │      │                ▼                      │
  │      │            「えっと…」                 │
  │      │                │                      │
  │      │                ▼ 0.45秒あける          │
  │      ▼                │                      │
  │   返答 ───────────────┴──> 文ごとに読み上げ    │
  │                                    │         │
  └────────────────────────────────────┘         │
         読み上げが終わったら聞き取りに戻る          │
```

### 通話の持ち主

通話できるのは1台までです。サーバーが持ち主の名札（端末がランダムに作る文字列）と最後に確認した時刻を覚えています。

```
通話をはじめる  → POST /api/call  名札を置く。先客がいれば入れ替わる
通話のあいだ    → GET  /api/call  5秒ごとに「まだ自分の番か」を確かめる
                                  自分でなければ黙って通話をやめる
通話をやめる    → DELETE /api/call  名札を消す
```

確認が2分途切れた名札は無効として扱うので、PCが落ちたまま記録が残っても通話中のままにはなりません。取り上げられた側は名札を消しません。新しい持ち主の記録まで消してしまうためです。

### 聞き取り

ブラウザの Web Speech API を使います。`continuous = false` / `interimResults = false` / `lang = "ja-JP"` で、1回の発話ごとに確定結果を1つ受け取ります。

- 認識は発話が切れるたびに終わるので、`end` イベントで開き直します
- `no-speech` と `aborted` は通話の終わりではないので、黙って聞き直します
- `not-allowed`（マイク不許可）は通話を終了します
- **読み上げ中はマイクを開きません。** スピーカーのままでも自分の声を拾いません。そのぶん割り込みはできません

認識結果には句読点も疑問符も付きません。「もしもし聞こえる」のような形で届きます。

### 間つなぎ（フィラー）

| 項目 | 内容 |
|---|---|
| 語 | 「あっ…」「えっと…」「んー…」「うーん…」 |
| 音声 | 通話の開始時にまとめて合成し、通話中は使い回す |
| 鳴らす条件 | 通話中／話し終わりから0.4秒たっても返答が未着／音声が1つ以上ある |
| 起点 | 認識の確定時ではなく**話し終わりの検知時**。確定までの数百ミリ秒も待ち時間のうち |
| 鳴らしたあと | 0.45秒あけてから本文へ。すぐ続けると畳みかけるように聞こえる |
| 語の選択 | 直前と同じ語は避ける。1つしか用意できていなければ繰り返す |

待ち時間は固定です。発言の長さや言い回しでは変えていません。プロンプト1900字のうち発言が占めるのは14字ほどで、何を話してもことはが読む量はほぼ同じだからです。過去368往復で測った「発言の長さと返答の長さ」の相関は +0.24 と弱く、尋ねる言い回しを含む場合でも返答が1.2倍になる程度でした。

音声エンジンが応じないときは、間つなぎなしで動きます。

### 発話

読み上げは句点・感嘆符・改行で文に分け、**1つ目を鳴らしながら次を合成**します。

```
   0.0s  1つ目の合成をはじめる
   1.0s  合成おわり → すぐ2つ目の合成をはじめる
   1.0s  ▶ 1つ目を再生
   2.0s  2つ目の合成おわり（再生中に間に合う）
   2.5s  ■ 1つ目おわり
   2.5s  ▶ 2つ目を再生（待ちなし）
```

- 10文字に満たない断片は前につなぎます。細切れに合成すると間延びするためです
- 合計300文字で打ち切ります。切れ目のない長文は、その位置で切り詰めて読みます
- 音声の長さは合成時間の2倍以上あるので、1つ目を鳴らしているあいだに残りは作り終わります
- 世代番号で打ち切れるようにしてあり、通話を切ると次の文へ進みません

## プロンプトの組み立て

空のブロックは飛ばし、残りを空行2つでつないで、1件のuserメッセージとして送ります。

| 順 | ブロック | 出どころ | 実測 |
|---:|---|---|---:|
| 1 | 固定ルール | `prompts/fixed_rules.txt` | 744字 |
| 2 | 人格 | `prompts/persona.txt` | 330字 |
| 3 | 時刻 | 下記 | 85字 |
| 4 | 基本情報 | 保護記憶 最大5件 | 93字 |
| 5 | 関連記憶 | 想起した記憶 最大6件 | 459字 |
| 6 | 直近の会話 | 最大5往復・3,000字 | 156字 |
| 7 | 今回の発言 | 入力そのまま | 14字 |
| | 合計 | | **約1,900字** |

実測は会話が途切れている状態のものです。続けて話すと6が積み上がり、4,700字ほどまで増えます。

記憶の各行は `- [id:12][2026-09-17][semantic/fact] 本文` の形です。日付はエピソードなら発生日、意味記憶なら確認日を使います。

### 時刻ブロック（3）

```
現在: 2026-09-17 13:26（木曜日）
前回の会話: 3日前
今のことは: 夜更かし中で、ゲームかスマホを触っている
今の機嫌: ふつう（とくに変わったところはない）
```

| 行 | 決め方 |
|---|---|
| 現在 | ローカル時刻。曜日は日本語 |
| 前回の会話 | `last_conversation_at`（UTC）からの経過を「たった今／3分前／5時間前／昨日／3日前／1週間前／2か月前／1年以上前」に言い換える。UTCのまま渡すと時差ぶん開いて見えるため |
| 今のことは | 時間帯ごとの様子。区切りは画面のアバター切り替え（`getAvatarGroup()`）と揃えてある |
| 今の機嫌 | `app_state.mood`。6時間を過ぎたものは「ふつう」に戻す |

## Geminiとのやりとり

### 送るもの

OpenAI互換の `/chat/completions` に、httpx で1回のPOSTを送ります。ストリーミングは使いません。

```json
{
  "model": "<GEMINI_MODEL>",
  "messages": [{"role": "user", "content": "<組み立てたプロンプト>"}],
  "max_tokens": 1024,
  "temperature": 0.7
}
```

`model` / `max_tokens` / `temperature` は設定値です（既定は順に `gemini-3.5-flash-lite` / 1,024 / 0.7）。整理のときだけ `max_tokens` を 1,500 に上げます。

system ロールは使わず、固定ルールも人格もすべて1件のuserメッセージに含めます。会話も記憶も履歴として渡すのではなく、テキストとして埋め込みます。

### 受け取るもの

`choices[0].message.content` を取り出します。本文の末尾に内部制御タグが付きます。

| タグ | 用途 | 扱い |
|---|---|---|
| `[USED: 1,2]` | 使った記憶のID | 数字だけ取り出す。Fastでは保護記憶のIDだけ通す |
| `[MOOD: 眠い]` | いまの機嫌 | 5つのラベル以外は捨てて直前の機嫌を保つ |

どちらも本文と保存する履歴から取り除きます。閉じ括弧が欠けた場合や全角の `［］：` でも拾えるよう、括弧は任意として行末までを上限に探します。取りこぼすとタグがそのまま画面に出るためです。

### 失敗したとき

| 状況 | 動作 |
|---|---|
| 通信エラー / 429 / 5xx / 空の応答 | 同じ内容で再試行。合計 `LLM_ATTEMPTS`（既定2）回まで。待ち時間は入れない |
| 400 / 401 | 即エラー。キーやモデル名の問題として扱う |
| その他の非200 | 即エラー |
| 応答の形が違う | 即エラー |

失敗しても作り話は保存しません。CUIは画面に出し、WebはHTTP 502を返します。

## 記憶の想起

### Fast / Slow

`KOTOHA_FAST_ENABLED` は既定で `false` なので、**通常はすべてSlowを通ります**。有効にした場合の判定は次のとおりです。

```
FAST_ENABLED が false            → slow
入力が FAST_MAX_CHARS（40字）超  → slow
質問・過去参照・記憶操作の語を含む → slow
入力が登録済みタグと一致          → slow
それ以外                         → fast
```

Fastは保護記憶だけを積みます。返答の1行目が `NEEDS_SEARCH` なら、同じターンのうちにSlowで生成し直します（`mode` は `slow+fallback`）。別のモデルに切り替えるわけではありません。

### 集め方（Slow）

```
① 入力＋直近の会話に、登録済みタグが文字として含まれるか調べる
      │
      ├─ 含まれる ──> ② そのタグを持つ記憶を集める            最大40件
      │                    並び順: タグの利用回数
      │                          → 記憶の最終利用日時
      │                          → 確認日時
      │                    │
      │                    └─> ③ ②の記憶から1本たどった先を足す  最大40件
      │
      └─ 含まれない ─────────────────┐
                                     │
④ 最近のエピソードと継続話題を足す ←──┘（タグの一致に関わらず必ず行う） 最大10件
      ↓
⑤ IDで重複を除き、保護記憶を別枠にして、残りを6件まで
```

②と③はタグが一致したときだけ動きます。④は毎回動くので、タグが1つも当たらなくても最近の出来事と続いている話題は渡ります。

- タグ照合は部分一致です。埋め込みや類似度は使いません
- 期限切れの記憶はすべての段階で除きます
- ②の並び順により、よく思い出す記憶が先に来ます。利用回数は0〜3で頭打ち、30日使わなければ0に戻るので、古い記憶が居座り続けることはありません
- 保護記憶は別に最大5件取ります（④とは独立）

## 記憶整理

### いつ走るか

| きっかけ | 条件 |
|---|---|
| CUI 起動時・返答後 | 未処理が `CONSOLIDATE_TURNS`（10）ターン以上 |
| CUI `/consolidate` | 無条件 |
| Web 巡回（60秒ごと） | 未処理があり、**最後の会話から5分以上たっている** |
| `kotoha.bat consolidate` | 無条件 |

Web が会話中に走らせないのは、巡回が `/api/chat` と同じロックを取るためです。整理のあいだ返答が数秒止まり、通話ではそれが沈黙になります。1回で20ターンまで処理できるので、溜めても間があけば追いつきます。

### 流れ

```
① 未処理の発言を切り出す
      last_processed_message_id より後で extractable=1
      最大20ターン・20,000字
      先頭の1件は上限を超えていても必ず含める
      ↓
② 再固定化の候補を読む
      pending_reconsolidation_ids のノード
      ↓
   ①も②も空 → 何もせず終了（APIを呼ばない）
      ↓
③ プロンプトを組む
      consolidation_system.txt
      ＋ 未処理の会話（[id:N] 付き）
      ＋ 既存の記憶（会話に含まれるタグから最大10件）
      ＋ 最近使われた記憶（②）
      ↓
④ Gemini に投げる（max_tokens 1,500）
      ↓
⑤ 最初の { から最後の } までをJSONとして読む
      読めなければエラー。処理位置は進めない
      ↓
⑥ 中身を検証して保存
      ↓
⑦ 後始末
      last_processed_message_id を①の末尾へ
      last_consolidation_at を更新
      pending_reconsolidation_ids を空に
```

①で先頭の1件を必ず含めるのは、上限を超える発言が1つ来たときに空を返すと、処理位置が永久に進まなくなるためです。長すぎる本文はプロンプト生成時に切り詰めます。

### JSONの検証（⑥）

モデルの出力はそのままでは信用せず、項目ごとに落とします。

**new_nodes**（最大8件）

| 条件 | 満たさないとき |
|---|---|
| `layer` が episode または semantic | その要素を捨てる |
| semantic の `kind` が fact / preference / open_topic / procedure | 捨てる（episode は event に固定） |
| `text` が空でなく、episode 400字・semantic 200字以内 | 捨てる |
| `source_message_ids` に今回のバッチ内のIDが1つ以上ある | 捨てる |

通ったものは `source_key = batch:<先頭id>-<末尾id>:<番号>` で登録します。同じキーがあれば無視されます。期限は最初の根拠発言の日時にエピソード30日／意味記憶180日を足した値です。タグは前後の空白を詰めて24字まで、最大3個です。

**edges**：`relation` が `derived_from` で、from/to がどちらも今回作れたノードを指しているものだけ登録します。

**reconfirm_ids**：整数のIDについて確認日時を更新し、期限を延長します。

**updates**（最大4件）：本文を200字までに切り、確認日時の更新・期限の延長・出典の追加・タグ利用回数のリセットを行います。根拠IDが今回のバッチ内にないものは捨てます。

会話中に記憶の本文が書き換わることはありません。既存ノードの自動統合と、承認を挟む仕組みはありません。

## 所要時間の目安

通話で話しかけてから声が返るまでの内訳です。★は実測、それ以外は目安です。

| 段階 | 時間 | 変わる要因 |
|---|---|---|
| 認識の確定 | 0.3〜0.8秒 | 発話の長さ、ネットワーク |
| ロック待ち | 通常 0秒 | 忘却やバックアップと重なったとき |
| 記憶検索・組み立て | 数ミリ秒 | ほぼ無視できる |
| 最初の1文字まで | 0.3〜1.0秒 | プロンプト長（1,900〜4,700字） |
| 生成 | 0.3〜0.8秒 | 返答の長さ（★平均25字） |
| 音声合成 | 1.1〜1.7秒 | ★0.74秒＋文字数×0.039秒 |
| | **合計 2〜4秒** | |

**いちばん重いのは音声合成です。** 文ごとに分けて先読みしているのは、ここを縮めるためです。

テキストの会話では認識と合成がないぶん、返答が出るまで1〜2秒ほどになります。

## 調整の早見表

変えたいものから引く表です。「反映」は変更が効くようになる条件です。

### 人格・話し方

| 変えたいこと | 直す場所 | 反映 |
|---|---|---|
| 性格、口調、呼び方、好み | `prompts/persona.txt` | **次の発言から**（再起動不要） |
| 守らせたい規則、やってほしくないこと | `prompts/fixed_rules.txt` | **次の発言から** |
| 記憶の抽出方針、JSONの出力形式 | `prompts/consolidation_system.txt` | **次の整理から** |
| 機嫌の種類と、それぞれの振る舞い | `talk/chat.py` の `MOODS` | サーバー再起動 |
| 機嫌を引きずる時間（既定6時間） | `talk/chat.py` の `MOOD_DECAY_SECONDS` | サーバー再起動 |
| 時間帯ごとの様子 | `talk/chat.py` の `situation()` | サーバー再起動 |
| 前回からの間隔の言い回し | `talk/chat.py` の `elapsed_phrase()` | サーバー再起動 |

プロンプトの3ファイルは毎回読み直しているので、**保存するだけで次の発言から効きます**。文面を試しながら詰めるときに便利です。

> ⚠️ **`MOODS` を変えたら `fixed_rules.txt` のラベル一覧も直してください。** 片方だけ変えると、モデルが返すラベルが未知の値になり、機嫌が一切変わらなくなります。ずれるとテストが落ちるようにしてあります。

> ⚠️ **`situation()` の時間帯を変えたら `serve/static/app.js` の `getAvatarGroup()` も直してください。** 画面のアバターと言うことが食い違います。こちらもテストで見ています。

### 会話の組み立て

| 変えたいこと | 直す場所 | 反映 |
|---|---|---|
| 参照する直近会話の量 | `.env` の `KOTOHA_RECENT_TURNS` / `_RECENT_CHARS` | サーバー再起動 |
| 返答の最大の長さ | `.env` の `KOTOHA_MAX_OUTPUT_TOKENS` | サーバー再起動 |
| 返答のばらつき | `.env` の `KOTOHA_TEMPERATURE` | サーバー再起動 |
| モデル | `.env` の `GEMINI_MODEL` | サーバー再起動 |
| 応答待ちの上限、再試行の回数 | `.env` の `KOTOHA_TIMEOUT_SECONDS` / `_LLM_ATTEMPTS` | サーバー再起動 |
| Fastルートの有効化と判定文字数 | `.env` の `KOTOHA_FAST_ENABLED` / `_FAST_MAX_CHARS` | サーバー再起動 |
| Fast/Slow を分ける語 | `talk/router.py` の `QUESTION_WORDS` ほか | サーバー再起動 |

> ⚠️ **`KOTOHA_RECENT_CHARS` を増やすと返答が遅くなります。** プロンプトがそのまま伸び、最初の1文字までの時間が延びます。既定の3,000字で、続けて話したときの全体が4,700字ほどです。

> ⚠️ **`KOTOHA_FAST_ENABLED=true` にすると、1ターンで2回生成することがあります。** Fastで足りないとモデルが判断すると `NEEDS_SEARCH` を返し、Slowでやり直すためです。

### 記憶

| 変えたいこと | 直す場所 | 反映 |
|---|---|---|
| 整理を始めるターン数（CUIのみ） | `.env` の `KOTOHA_CONSOLIDATE_TURNS` | 次回起動 |
| 会話が途切れたと見なす時間 | `.env` の `KOTOHA_IDLE_SECONDS` | サーバー再起動 |
| 巡回の間隔 | `.env` の `KOTOHA_BACKGROUND_INTERVAL_SECONDS` | サーバー再起動 |
| 1回の整理で扱う量 | `.env` の `KOTOHA_BATCH_TURNS` / `_BATCH_CHARS` | サーバー再起動 |
| 記憶の保持日数 | `.env` の `KOTOHA_EPISODE_DAYS` / `_SEMANTIC_DAYS` | サーバー再起動 |
| 想起する件数 | `.env` の `KOTOHA_PINNED_LIMIT` / `_RELATED_LIMIT` ほか | サーバー再起動 |
| 忘却を回す間隔 | `.env` の `KOTOHA_MAINTENANCE_SECONDS` | サーバー再起動 |
| 1回に作る記憶の上限（既定8件） | `memory/consolidate.py` の `MAX_NEW_NODES` | サーバー再起動 |
| 記憶本文の字数上限 | `memory/consolidate.py` の `_validate_and_save` | サーバー再起動 |

> ⚠️ **`KOTOHA_CONSOLIDATE_TURNS` はCUIだけで使います。** Webは会話が途切れてから整理する方式なので、この値を変えても挙動は変わりません。Web側の頃合いは `KOTOHA_IDLE_SECONDS` です。

> ⚠️ **保持日数を変えても、すでにある記憶の期限は書き換わりません。** 新しく作る記憶と、想起・再確認で延長するときに使われます。

> ⚠️ **記憶本文の字数上限を変えるときは、`consolidation_system.txt` に書いてある字数も揃えてください。** プロンプト側が400字と言っているのに検証が200字で切ると、作られた記憶が黙って捨てられます。

### 声と通話

| 変えたいこと | 直す場所 | 反映 |
|---|---|---|
| 話者（声） | `.env` の `KOTOHA_VOICE_STYLE_ID` | サーバー再起動 |
| 読み上げの有効・無効 | `.env` の `KOTOHA_VOICE_ENABLED` | サーバー再起動 |
| 音声エンジンの場所 | `.env` の `KOTOHA_VOICE_BASE_URL` | サーバー再起動 |
| 間つなぎの語 | `serve/static/app.js` の `FILLERS` | ブラウザ再読み込み |
| 間つなぎを出すまでの待ち | `serve/static/app.js` の `FILLER_AFTER_MS` | ブラウザ再読み込み |
| 間つなぎのあとの間 | `serve/static/app.js` の `FILLER_GAP_MS` | ブラウザ再読み込み |
| 読み上げの分け方 | `serve/static/app.js` の `SENTENCE_END` / `SHORT_PART` | ブラウザ再読み込み |
| 読み上げの字数上限 | `serve/voice.py` の `MAX_CHARS` | サーバー再起動 |
| 声の速さ・高さ・抑揚 | `serve/voice.py` の `speak()`（クエリに `speedScale` などを足す） | サーバー再起動 |

> ⚠️ **話者IDはエンジンの `/speakers` で確認してください。** 存在しないIDだと合成が失敗し、読み上げだけが黙ります（会話は続きます）。

> ⚠️ **`FILLER_AFTER_MS` を300msより短くしないでください。** 速く返せた場面でも鳴るようになり、「えっと」と言った直後に即答する不自然さが出ます。

> ⚠️ **読み上げの字数上限は2か所にあります。** `voice.py` の `MAX_CHARS` と `app.js` の `SPEAK_MAX_CHARS` を同じ値にしてください。前者は1回の合成ぶん、後者は全体の合計に効きます。

### 外出先から直せるもの

画面の設定シートから直せるものは、ファイルを開かなくても変えられます。

| 変えたいこと | 画面の場所 | 直接直す場合 |
|---|---|---|
| 人格・決まりごと・整理の指示 | ことばを直す | `prompts/*.txt` |
| 返答のふり幅、返答の長さ、覚えている量、整理までの間、声の種類 | 設定を変える | `.env` |

> ⚠️ **画面に出していない設定は、画面からは変えられません。** 追加したいときは `serve/admin.py` の `SETTINGS` に項目を足してください。範囲もそこに書きます。リクエストを直接送っても、一覧にないキーは拒否されます。

> ⚠️ **「設定を変える」は `.env` を書き換えます。** コメント行と関係のない行は残しますが、書式が壊れていると読めなくなります。`settings.bat` で開いたときと同じファイルです。

### 共通の注意

- **編集するのは `.env` です。** `.env.example` は既定値の一覧なので、こちらを直しても `.env` にすでにある項目は上書きされません。`settings.bat` は `.env` に足りない項目だけを追記します。
- **`.env` を変えたらサーバーを止めて `start.bat` で入れ直してください。** 設定は起動時に一度だけ読みます。
- **数値には有効範囲があります。** 範囲外だと起動時に理由を表示して止まります。`settings.bat` の保存後チェックでも同じ検査が走ります。
- **`KOTOHA_DB_PATH` を変えてもデータは移りません。** 新しい場所に空のDBができます。移したいときはファイルを自分で移動してください。
- **`KOTOHA_BACKUP_KEEP` を減らすと、次のバックアップで古い世代が消えます。** 残したいファイルは先に別の場所へ退避してください。
- **変更したら `tests` を流してください。** 揃えるべき対のずれなど、いくつかは自動で気づけるようにしてあります。

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests
```
