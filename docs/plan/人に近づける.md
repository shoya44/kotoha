# 人に近づける（着手前の計画）

[09 解剖図](../09_解剖図.md) の「軽くした部分」を減らしていく。**進行中の計画**で、終わった段は [history/](../history/) に記録として移し、ここからは消す。

## 進め方の決まり

- **1段＝1 PR。** 段ごとに `python -m tools.check` が通ってから押す（CI と同じ検査）。
- **時間は `clock.py` 1本。** 日単位の経過は `tests/support.py` の `Clock` で止めて進める。SQLite の `'now'` は使わない（PR 0 で置き換え済み）。新しく `datetime.now()` を書かない。触ったモジュールは `clock.now()` に寄せる。
- **列を足すときは `MIGRATIONS`。** `SCHEMA` は新しいDBのため、`MIGRATIONS` は手元のDBのため。両方書く。
- **数字は測ってから決める。** 強さの初期値・減り方は、`KOTOHA_DEBUG` で `data/retrieve.log` を1週間ためて、`[USED:]` の比から置く。決めるまでは既定を保守的に（今の期限と同じ挙動になる値）。
- **プロンプトの語彙は変えない。** 機嫌のラベル、`[MOOD:]`、`[USED:]` はそのまま。中身だけ変える。

## 段1でやったこと（2026-09-22）

設計メモとの違いは1つ。`expires_at` をやめる代わりに、**強さから導いた「床を切る時刻」を `expires_at` に書く**ことにした。忘却の道・生存の判定・index が前のまま使え、列は `strength` と `strength_at` の2本で済んだ。

手元のDBの控え（6日分・2,420通・記憶190件）で改修前後の想起を比べた（LLM・Ollama は呼ばず、タグ命中だけ）。

| | 件 |
|---|---|
| 発言 | 1,199 |
| 渡す記憶が同じ | 877（73%） |
| 上位6件の中で並びが入れ替わる | 322（27%） |
| 何も渡さない | 0 |

入れ替わりは、確かめてから日が浅い意味記憶が、古い出来事より前に出る向き。逆算した強さの分布は、出来事の中央値 0.72、意味 0.95（新しいDBなので、まだ薄れていない）。
