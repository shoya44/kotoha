## 起きたことと、そこから決めたこと

どれも**黙って失敗していた**ものです。同じ形（`except ... pass`、あるいは結果を確かめない）で、気づくまでに時間がかかりました。いま何をしているかは [コンセプト](../01_コンセプト.md#原則) を参照してください。

### 通知が誰にも届いていなかった（2026-09-18）

宛先に `Subscribed Users` という束を指定していましたが、**この束はいまのアプリには存在しません**。OneSignalが最初に用意する束の名前は、アプリを作った時期で変わります。

無い束を指してもOneSignalは断らず、200を返したまま誰にも送りません。そして `push()` は状態コードしか見ていなかったので、「送った」と記録し続けました。**こちらの記録は13件、OneSignal側の控えは0件。**丸一日気づけませんでした。

→ 宛先を `Total Subscriptions` に変更。返事の本文まで見て、`errors` か宛先0件なら失敗として記録する。

### 裏の巡回が丸ごと止まっていた

順番待ちの名前を変えたとき、背景ループの側を直し忘れました。`NameError` は `except Exception: pass` に飲み込まれ、**記憶整理・バックアップ・忘却が静かに止まりました**。

→ ひと回りを `one_round()` にまとめ、落ちたものは必ず `data/notify.log` に残す。実際に一周させる回帰テストを追加。

### テストが本物の通知を送っていた（2026-09-18）

巡回をまるごと一周させるテストが、本物のGeminiを叩き、本物の通知を送っていました。**宛先が壊れていて誰にも届かなかったため、丸一日それに気づけませんでした。**宛先を直した直後のテストで、持ち主の電話が実際に10回鳴りました。

→ `tests/__init__.py` で外へつなぐ道を塞ぐ。黙って無視ではなく、その場で落とす。通知は既定で止め、鳴らす道を試すテストだけが自分で開ける。

### 同じ頼まれごとが2通届いた（2026-09-18）

12:00に鳴るはずだった頼まれごとは**1件**でしたが、会話に2件書かれ、通知も2通届きました。片方はことはの言葉、もう片方は定型の代役です。

原因は**往復の番号（`turn_id`）の採り方**でした。番号を見る文と書き込む文が分かれていたため、そのあいだに別の書き手が入ると同じ番号になり、`UNIQUE (turn_id, role)` で弾かれます。弾かれたほうが定型に落ち、2通目になりました。

```
① SELECT MAX(turn_id) + 1     ← 番号を見る
② INSERT INTO messages(...)   ← 別の文で書き込む
        ↑ ①と②のあいだに他が書き込むと、同じ番号になる
```

**どの2つが重なったのかは特定できていません。** ログとDBから言えるのは「2つが同時に動いた」ところまでで、静的に読むかぎり重ならないはずの組み合わせでした。そこで、重なり方を特定しなくても効く形に直しています。

直す前後で、6本の書き手が同時に書く場合を実際に測りました。

| 採り方 | 失敗 |
|---|---|
| 2文に分けて採る（直す前） | **5件**（すべて `IntegrityError`） |
| 1文の中で採る（直した後） | **0件** |

→ 番号は書き込みと同じ1文の中で採る（`db.start_turn`）。あわせて、見張りも言うときは順番待ちに並ぶ。

なお、この調査で `chat.reach_out()` が誰からも呼ばれていないことも分かりました。通知を通さず直接しゃべる道だったので、消しました。

### バックアップの失敗を握りつぶしていた

保存先の不調で忘却まで止めない、という判断自体は正しいものでした。ただ失敗を記録していなかったので、**控えが取れていないことに、要るときまで気づけません**。

→ 失敗を `data/notify.log` に残す。後段は今までどおり止めない。

## 決めごとの経緯（短いもの）

- **プロンプトの記憶行から層のラベルを外した。** 以前は `[id:12][2026-09-17][semantic/fact]` と36字あり、ラベルだけで本文と同じ量を占めていました。層は種類から決まるので書く必要がありません。`id` は `[USED:]` で返してもらうため残しています。
- **iPhoneのSafariは通知のボタンに対応していません。** 「あとでもう一度」を通知そのものに付けられないため、開いた画面に出す形にしてあります。Web Share Target も使えません。
- **記憶整理と通知は、3回続けて失敗したら諦めます。** 言えるまで毎分試すと、そのたびにGeminiの枠を1回ずつ食うためです。

### 脳が2つのプロセスで回っていた（2026-09-20）

トレイは終了コードの定数ひとつのために `serve.web` を取り込んでいた。`jobs.py` はモジュール直下で時計のスレッドを起こしていたので、**取り込んだ瞬間にトレイの中でも巡回が始まっていた**。`turn_lock` はプロセス内の錠なので、2つの巡回のあいだに排他はない。

確実に起きていた害は、API枠よりも計測のほうだった。`presence.sample` が両方から毎分呼ばれ、前面アプリの数えが2ずつ増える。`busy_with` はその数を「分」として返すので、**常駐しているかぎり、ことはは相手の様子を常に2倍で言っていた**。固定ルールの「していないことを、あるように言わない」に、コードのほうが恒常的に違反していた。

「同じ頼まれごとが2通届いた」も、静的に読むかぎり単一プロセスでは重ならない組み合わせだった。2つ目の書き手が import の副作用で隠れていた、と読むと辻褄が合う。

**決めたこと。** 仕事を始めるのは、脳として動き出すとき（`serve/web.py` の lifespan）だけ。取り込んだだけではスレッドも接続も始めない。終了コードは `config` へ移して、トレイが脳を取り込む理由そのものを消した。取り込んだだけで時計が立たないことを `tests/test_one_brain.py` が見張る。

### テストが本物のログに書き込んでいた（2026-09-20）

外への通信は塞いであったが、**書き置きは塞いでいなかった**。テストを走らせるたび、テストの出した「控えを置けなかった」「頼まれごとを畳んだ」が `data/notify.log` に並び、本物の記録に混ざっていた。事故を追おうとしてログを開いたときに気づいた。

**決めたこと。** `tests/__init__.py` で `notify.LOG_PATH` を一時フォルダーへ逃がす。外への通信を塞いでいるのと同じ考え方で、**持ち主が事故を追うための1本を汚さない**。

### マージしたはずのものが main に無かった（2026-09-20）

PRを積み重ね（stacked）にして、ベースを main ではなく前のPRのブランチにしていた。ベース側を先に main へマージしたあとに積んだPRをマージすると、**内容は中間ブランチに入って、そこで止まる**。GitHub上の表示は「MERGED」なので、気づけなかった。マージ済みのPRのブランチにコミットを足したときも同じことが起きた。

**決めたこと。** 積み重ねるときは、**ベース側より先に**積んだほうをマージする。マージ後のブランチには足さない。仕上げに `git log origin/main..origin/<branch>` で、取り残しが無いことを確かめる。


### 「database is locked」と、読めない控えの失敗（2026-09-23）

`notify.log` に「居場所を書き写せなかった: database is locked」が残った。巡回は前面アプリを数えて（`presence.sample`）そのまま記憶整理へ進み、Gemini の返事を待つ。**数えたぶんを閉じずに待っていた**ので、そのあいだ書き手は全員止まる。器の取次（`hub._remember`）は会話の順番待ちの外から別の接続で書くため、5秒待って諦めた。日誌が巻き戻し（rollback journal）だったので、読んでいるだけの相手にも書き手が待たされていた。

同じログに「控えのもう1本を置けなかった: FileExistsError」が数十行並んだ（9/19〜20）。`KOTOHA_BACKUP_DIR` がファイルを指していて `mkdir` が断っていたが、行を読んでも何を直せばよいか分からなかった。

**決めたこと。** 短い書き込みはその場で閉じる（`presence.sample` が commit する）。日誌は WAL にして、読む側と書く側が互いを待たないようにする（`db.connect`）。控えの置き場がフォルダーでないときは、そう書く。
