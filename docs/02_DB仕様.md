# ことは：DB仕様

運用設定の数値は既定値です。変更は `settings.bat` から `.env` で行います。設定一覧は [README](../README.md#設定の変更) を参照してください。

実装元は `kotoha/memory/db.py` の `SCHEMA` とDB操作関数です。

## 接続・初期化

既定の保存先はプロジェクト直下の `data/kotoha.sqlite3`。`KOTOHA_DB_PATH` で変更できます。接続時に親フォルダーを作成し、外部キー制約を有効化、ロック待機時間を5,000msに設定します。

`init` は `CREATE TABLE IF NOT EXISTS` などでテーブル・索引を作成します。既存スキーマの変更を適用するマイグレーション機構はありません。`start.bat` と `kotoha.bat web` はどちらも起動時にDBを初期化します。

## テーブル

| テーブル | 主なカラム | 制約・用途 |
|---|---|---|
| `messages` | id, turn_id, role, text, created_at, extractable | `(turn_id, role)` が一意。roleはuser/assistant |
| `memory_nodes` | id, layer, kind, text, occurred_at, confirmed_at, last_used_at, expires_at, pinned, source_summary, source_key | source_keyが一意。記憶本文と期限・保護状態 |
| `memory_edges` | from_id, to_id, relation | 3項目の複合主キー。自己接続禁止 |
| `memory_tags` | node_id, tag, use_count, last_used_at, last_used_turn_id | `(node_id, tag)` が主キー。use_countは0〜3 |
| `memory_sources` | node_id, message_id | 記憶と根拠発言の対応。2項目の複合主キー |
| `app_state` | key, value | アプリ状態を文字列で保存 |

`layer=episode` のkindは `event`。`layer=semantic` のkindは `fact`、`preference`、`open_topic`、`procedure` です。

接続のrelationは `derived_from` と `related_to` を許可します。整理処理が新規ノード間に `derived_from` を、座標づけの巡回が意味の近い記憶どうしに `related_to` を登録します。

`source_summary` はカラムとして存在しますが、現在の整理処理では書き込みません。

## 索引

`messages(created_at, id)`、`memory_tags(tag, node_id)`、`memory_nodes(expires_at)`、`memory_nodes(layer, confirmed_at)`、`memory_edges(from_id, relation)`、`memory_edges(to_id, relation)`、`memory_sources(message_id, node_id)` に索引があります。

## アプリ状態

| キー | 内容 |
|---|---|
| `last_processed_message_id` | 整理済みの最終メッセージID。初期値0 |
| `last_conversation_at` | 返答の保存時刻 |
| `last_consolidation_at` | 整理完了時刻 |
| `last_forget_at` | メンテナンス実行時刻 |
| `pending_reconsolidation_ids` | 最近使った記憶のID。カンマ区切り、最大50件 |
| `last_backup_at` | 自動バックアップの実行時刻。手動実行では更新しない |
| `mood` | 直前の返答が申告した機嫌のラベル |
| `mood_at` | その機嫌を記録した時刻。6時間で既定値に戻す |

`process_generation` は加算されるだけで参照されていなかったため廃止しました。既存DBに残る行は無害です。

## 日時・保持・削除

アプリが生成する時刻はUTCの `YYYY-MM-DDTHH:MM:SSZ`。新規記憶の `occurred_at` は通常 `YYYY-MM-DD` です。

新規記憶の期限は最初の有効な根拠発言の日時を基準とし、エピソード30日、意味記憶180日を加算します。想起・再確認・本文更新では、その時点から同じ日数だけ `expires_at` を延ばします。既存値との大きいほうを採るので期限は縮まらず、`expires_at` が未設定のノードは未設定のままです。

メンテナンスは、保護されていない期限切れノードの削除、30日未使用タグの利用回数リセット、最終忘却時刻の更新を行います。会話原文の削除、容量上限、VACUUMの自動実行はありません。

期限やタグ利用日時の比較は文字列のままで行いますが、比較相手も `strftime('%Y-%m-%dT%H:%M:%SZ', 'now')` で保存形式に揃えているため、同じ日のうちに切れた期限も取りこぼしません。列に関数を当てないので索引も利きます。

ノード削除時は、外部キーのCASCADEにより関連する接続・タグ・出典リンクも削除します。他の記憶ノード、原文、バックアップは残ります。保護は `pinned` だけを変更し、期限を消しません。検索にも期限条件があるため、保護した記憶が常に想起対象になるとは限りません。

## バックアップ

SQLiteのbackup APIでDBをコピーします。保存先はDBと同じフォルダーの `backups/` で、最新7件を超えたバックアップを削除します。前回から24時間が経っていれば、Webのバックグラウンド処理とCUIの終了時に自動で作成します。いずれも忘却より先に実行するため、期限切れで消えたノードも直前のバックアップには残ります。`backup` コマンドによる手動作成は `last_backup_at` を更新せず、自動実行の間隔に影響しません。復元時はCUI・Webを停止し、既存DBを退避してから置き換えます。

`KOTOHA_BACKUP_DIR` を設定すると、取れた控えを**もう1本そこへも置きます**（最新7件は同じ）。既定は空欄で、DBの隣だけです。ことはの本体は記憶なので、隣の1本だけだとディスクが1枚壊れた日にすべて消えます。別ドライブ・NAS・同期フォルダーを指してください。置けなかったときは `data/notify.log` に残り、隣の1本は普通に取れます。
